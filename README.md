# Swag Labs Web Automation

A maintainable UI test automation framework for the [Swag Labs Application](https://www.saucedemo.com/), built with **Java 21, Selenium WebDriver, TestNG, and Maven**.

The framework follows the **Page Object Model (POM)** to improve maintainability, reusability, and test organization. It supports smoke and regression testing, configurable browser execution, centralized configuration, logging, and Allure reporting.

## Overview

This project automates core Swag Labs workflows, including login, product listing and sorting, cart operations, and menu functionality.

### Key Features

- Page Object Model for organized page interactions and locators
- TestNG annotations, data providers, and test grouping
- Smoke and regression test suites
- Configurable browser and headed/headless execution
- Reusable browser actions and wait utilities
- Centralized URL and environment configuration
- Logging with SLF4J and Logback
- Allure TestNG reporting integration
- Optional screen recording support

## Technology Stack

| Technology | Purpose |
|---|---|
| Java 21 | Programming language |
| Maven | Build and dependency management |
| Selenium WebDriver | Browser automation |
| TestNG | Test execution and test organization |
| WebDriverManager | Browser driver management |
| Allure TestNG | Test reporting |
| AspectJ Weaver | Supports applicable Allure annotations |
| SLF4J + Logback | Logging |

Dependency versions are managed in `pom.xml`.

## Framework Structure

```text
swag_lab_web_automation/
├── pom.xml
├── .env.example
├── .env                         # Local configuration; not committed
├── SmokeTestSuite.xml
├── RegressionTestSuite.xml
└── src/
    ├── main/java/
    └── test/
        ├── java/
        │   ├── pages/           # Page objects and locators
        │   ├── testcases/       # TestNG test classes
        │   └── utilities/       # Driver, configuration, URLs, listeners
        └── resources/
            └── logback.xml      # Logging configuration
```

`target/` is generated by Maven and contains build output, test reports, and other execution artifacts.

### Main Components

- **`pages/`** — Contains page objects, element locators, and reusable page actions.
- **`testcases/`** — Contains test scenarios, validations, and assertions.
- **`BaseDriver.java`** — Manages WebDriver setup, browser configuration, and teardown.
- **`ConfigReader.java`** — Reads configuration from supported configuration sources.
- **`URLs.java`** — Centralizes application URLs.
- **`TestListener.java`** — Handles test lifecycle events and logging.
- **`VideoRecorder.java`** — Provides screen-recording functionality when configured.
- **`SmokeTestSuite.xml`** — Selects tests belonging to the smoke group.
- **`RegressionTestSuite.xml`** — Selects tests belonging to the regression group.

## Configuration

The framework uses `.env` for local configuration and `.env.example` to document the required configuration keys without exposing actual values.

### 1. Create the `.env` File

The `.env.example` file is a template. Create a separate `.env` file in the project root, at the same level as `pom.xml`.

Copy the contents of `.env.example` into `.env`, then replace the placeholders with values appropriate for your environment.

Example `.env.example`:

```dotenv
# Application Configuration
BASE_URL=YOUR_APPLICATION_URL

# Browser Configuration
BROWSER=YOUR_SUPPORTED_BROWSER
MODE=headed

# Optional: Chromium executable path
CHROMIUM_PATH=YOUR_CHROMIUM_EXECUTABLE_PATH

# Login Credentials
LOGIN_USER=YOUR_TEST_USERNAME
LOGIN_PASSWORD=YOUR_TEST_PASSWORD

# Optional: Additional test users
LOCKED_OUT_USER=YOUR_LOCKED_OUT_USERNAME
PROBLEM_USER=YOUR_PROBLEM_USERNAME
PERFORMANCE_GLITCH_USER=YOUR_PERFORMANCE_TEST_USERNAME
ERROR_USER=YOUR_ERROR_TEST_USERNAME
VISUAL_USER=YOUR_VISUAL_TEST_USERNAME
```

**Important:** The values above are placeholders, not working configuration values. Replace them in your local `.env` file. The variable names must match those referenced by your Java code.

### 2. Configuration Reference

| Variable | Purpose |
|---|---|
| `BASE_URL` | Base URL of the application under test |
| `BROWSER` | Browser to launch, according to the supported values in `BaseDriver.java` |
| `MODE` | Browser execution mode, such as `headed` or `headless` |
| `CHROMIUM_PATH` | Optional executable path when using the Chromium browser option |
| `LOGIN_USER` | Username used by standard login tests |
| `LOGIN_PASSWORD` | Password used by login tests |
| `LOCKED_OUT_USER` | Username for locked-out user scenarios |
| `PROBLEM_USER` | Username for problem-user scenarios |
| `PERFORMANCE_GLITCH_USER` | Username for performance-glitch scenarios |
| `ERROR_USER` | Username for error-user scenarios |
| `VISUAL_USER` | Username for visual-test scenarios |

Only configure the additional user variables if the corresponding tests use them. Confirm that all keys match the names referenced in `ConfigReader.java` and the relevant page objects.

### 3. Browser Configuration

Set `BROWSER` to a value supported by your current `BaseDriver.java` implementation.

Common browser options include:

- `chrome` — Google Chrome
- `firefox` — Mozilla Firefox
- `edge` — Microsoft Edge
- `chromium` — Chromium, if supported by the configured browser factory

For visible browser execution:

```dotenv
BROWSER=chrome
MODE=headed
```

For headless execution:

```dotenv
BROWSER=chrome
MODE=headless
```

The Chromium executable path is platform-specific. Set `CHROMIUM_PATH` only when required by your implementation.

### 4. Configuration Priority

The configuration reader may resolve values in the following order, depending on its implementation:

1. Java system properties
2. Operating-system environment variables
3. Values from `.env`
4. Default values defined in Java code

Verify the actual precedence in `ConfigReader.java`.

For example, to override the browser mode for a single run:

```bash
mvn clean test -DsuiteFile=SmokeTestSuite.xml -DBROWSER=chrome -DMODE=headless
```

### 5. Protect Local Configuration

Add these entries to `.gitignore`:

```gitignore
# Environment configuration
.env
.env.*

# Allow the example template
!.env.example

# Maven output
target/

# IDE files
.idea/
*.iml
.classpath
.project
.settings/

# Operating system files
.DS_Store
Thumbs.db
```

Commit `.env.example` so other developers can understand the required configuration. Do not commit your local `.env` file.

## Prerequisites

Install the following before running the framework:

1. **JDK 21**
2. **Maven 3.8 or later**
3. A supported browser, such as Google Chrome, Firefox, or Microsoft Edge
4. **Allure CLI**, if you want to generate and open Allure reports from the command line

Verify your installation:

```bash
java -version
mvn -version
```

Ensure that Java 21 is configured as your project JDK.

## Run Tests

Run commands from the project root directory.

### Run the Default Suite

```bash
mvn clean test
```

This runs the default suite configured in your Maven and TestNG setup.

### Run the Smoke Suite

```bash
mvn clean test -DsuiteFile=SmokeTestSuite.xml
```

### Run the Regression Suite

```bash
mvn clean test -DsuiteFile=RegressionTestSuite.xml
```

### Run in Headed Mode

```bash
mvn clean test -DsuiteFile=SmokeTestSuite.xml -DMODE=headed -DBROWSER=chrome
```

### Run in Headless Mode

```bash
mvn clean test -DsuiteFile=RegressionTestSuite.xml -DMODE=headless -DBROWSER=chrome
```

The suite XML files determine which tests execute. Ensure the TestNG groups referenced in the XML files match the groups assigned to your test methods.

**Parallel execution:** If the suite runs methods in parallel, ensure that each test receives its own WebDriver instance and does not depend on another test's browser state or execution order.

## Reports and Artifacts

### Maven and TestNG Reports

After execution, inspect:

```text
target/surefire-reports/
```

This directory contains test execution reports and failure details.

### Allure Reports

After running the tests, generate the Allure report:

```bash
allure generate target/allure-results --clean -o target/allure-report
```

Open the generated report:

```bash
allure open target/allure-report
```

The `target/allure-results/` directory must contain result files before you generate the report. If the directory is empty, verify your Allure TestNG integration and test configuration.

### Screen Recordings

If screen recording is enabled by the framework, recordings may be saved under:

```text
target/videos/
```

Recording depends on the implementation and the availability of a supported graphical desktop session. Check `VideoRecorder.java` and the test lifecycle configuration for the actual recording behavior and output location.

Generated reports, videos, screenshots, and build output should generally not be committed to version control.

## Test Coverage

The test suite is organized around core application workflows:

- **Login** — Login page appearance, valid credentials, empty fields, invalid credentials, and locked-out user behavior.
- **Products** — Product listing, product details, and sorting behavior.
- **Cart** — Cart operations and related validations.
- **Menu** — Menu interactions and navigation.
- **Footer** — Footer information and social links, where implemented.

The actual coverage depends on the test methods currently present in `src/test/java/testcases/`.

## How to Add a Test

1. Identify the relevant page object in `src/test/java/pages/`.
2. Add or update locators and reusable page actions in the page layer.
3. Create or update the test class under `src/test/java/testcases/`.
4. Add the appropriate TestNG group:
    - `smoke` for critical functionality.
    - `regression` for broader functional validation.
    - Both groups if the test belongs in both suites.
5. Use clear method names, descriptions, and assertions.
6. Execute the relevant suite and review the results.

Example TestNG test:

```java
@Test(
    groups = {"smoke", "regression"},
    description = "Verify the products page is displayed"
)
public void productsPageIsDisplayed() {
    // Arrange and act using the existing page objects.
    // Assert the expected page state.
}
```

Follow the existing framework conventions when implementing new tests.

## Troubleshooting

| Problem | What to Check |
|---|---|
| Browser does not start | Confirm the browser is installed and the browser name is supported by `BaseDriver.java`. |
| Wrong application URL | Check `BASE_URL` and the configuration priority in `ConfigReader.java`. |
| Tests are not executed | Verify TestNG annotations, suite XML configuration, test groups, and Maven test discovery. |
| Tests fail intermittently | Use appropriate explicit waits, stable locators, and independent test data. |
| Allure report is empty | Confirm that test execution generated files under `target/allure-results/`. |
| Recording is missing | Check the recording utility, test lifecycle, browser mode, and output directory. |
| Configuration is not loaded | Verify that `.env` is in the project root and that its keys match the Java configuration references. |

## Security

- Keep `.env` excluded from Git.
- Use `.env.example` to document configuration keys without actual credentials.
- Never commit passwords, access tokens, or production secrets.
- Avoid logging sensitive values.
- If credentials have been exposed in a remote repository, rotate them and address the exposed Git history.
